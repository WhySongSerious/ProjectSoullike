# 역할 분담과 스크럼 계획

갱신일: 2026-09-23 / 확정 목표일: 2026-11-23 / 시간대: Asia/Seoul.
사용자가 확정한 범위는 3명 구성·11/23 마감·머신러닝 기반 동적 난이도 필수 구현·스크럼 운영입니다. 주간 가용시간·SP·세부 모델/수집 기준은 팀 계획에서 확정합니다.

## 목표

보스 1종·전투 공간 1개에서 시작→교전→승리 또는 사망→재시작을 끝까지 플레이할 수 있는 데모. 기존 이동·카메라·콤보·락온·골렘 상태 머신을 확장합니다. 학습 데이터 수집부터 모델 학습·게임 내 추론·동적 난이도 비교 검증까지 필수로 포함합니다. 전체 게임/추가 스테이지 제작은 이번 최소 목표에 포함하지 않습니다.

| 송재혁 | 팀장, 우선순위·범위 결정, 스크럼 진행, 통합 | 플레이어·VFX·애니메이션·ML 총괄(수집 구조·전처리·학습·평가·Unity 추론) | 지민과 코드 상호 리뷰, 다윤과 연출 검수 |

3인 팀이므로 별도의 관리 전담자를 두지 않습니다. 재혁은 제품 우선순위 결정과 스크럼 진행을 겸하고, 다윤은 기획 수용 기준을 준비합니다. 매 스프린트의 실제 수행량은 세 명이 함께 정합니다.

재혁의 관리·통합·VFX 과부하를 막기 위해 주간 가용시간의 약 60~70%만 기능 작업으로 계획하고 나머지를 리뷰·통합·버그 대응에 남깁니다. 다윤에게 코딩 역량을 가정하지 않습니다. UI 코드 연결은 재혁, 보스 모션 연결은 지민이 맡고 다윤은 리소스와 적용 기준을 제공합니다.

재혁의 ML 책임이 가장 큽니다. S3까지 핵심 VFX/애니메이션을 우선 완성하고 S4~S7은 수집 파이프라인→데이터 품질→학습→게임 적용을 주 작업으로 삼습니다. S5의 수집 운영·라벨링은 다윤이, S5의 보스 조절 인터페이스와 S7의 RC 검증은 지민이 맡아 병목을 줄입니다. 모델/데이터 관련 최종 기술 판단은 재혁이 담당합니다.

## 머신러닝 동적 난이도 최소 구현안

아래 기술 방식은 실행 가능한 계획 초안이며 사용자 지정 알고리즘이 아닙니다. 모델·특징량·라벨·평가 기준은 #21에서 확정합니다.

1. **명세 #21:** 플레이 기록에서 예측할 값(예: 체감 난이도/적정 난이도 단계), 수집 특징량, 라벨 기준, 적용 시점 정의.
2. **수집 #22~#23:** 게임 이벤트와 세션 요약을 버전 있는 파일로 내보내고 고정 난이도 파일럿→본 수집 진행. 익명 참가자/세션 ID·게임/데이터 버전·당시 난이도를 기록.
3. **학습 #24:** 우선 오프라인 지도학습의 작은 모델을 제안. 참가자별 학습/검증/최종 평가 분리, 학습 데이터로만 전처리 fit, 기준선 비교, 재현 방법·모델 버전 기록.
4. **적용 #25~#26:** 지민의 보스 조절 API에 재혁의 학습 모델 출력을 연결. 전처리 일치·추론 비용·조절 간격/상하한 확인.
5. **검증 #27:** 학습에 쓰지 않은 참가자/세션으로 고정 난이도와 비교. 모델 지표와 실제 플레이 경험을 함께 보고.

공격 시도/적중, 회피 시도/성공, 피격·사망, 전투 시간, 난이도 설정, 주관 난이도 등은 수집 후보입니다. 예측 시점 이후 결과를 입력 특징에 섞지 않으며 미래 결과를 라벨로 사용할 경우 입력 관측 구간과 분리합니다. 수집 규모는 파일럿 전에 목표를 정하고 실제 분포·품질을 보며 보완합니다. 데이터가 충분하다고 미리 가정하거나 효과 향상을 보장하지 않습니다.

원시 개인별 플레이 로그는 접근 제한 위치로 관리하고, 공개 저장소에는 스키마·합성 예제·집계 결과를 둡니다. 조절은 전투 사이 또는 정한 안전 구간에 적용하며 이미 시작한 공격의 예고/판정을 갑자기 바꾸지 않습니다. 입력 부족·추론 실패 시 고정 난이도 폴백과 수동 비활성화를 제공합니다. **규칙 기반 폴백만으로 ML 구현을 완료 처리하지 않습니다.**

## 회의와 기록

- 주초 계획 30분: 스프린트 목표 1개, 개인 가용시간, Ready 작업, 예상 검증 방법 합의.
- 매일 10분 이내: 완료한 것/오늘 할 것/막힘을 이슈 진행 기록으로 공유. 필요할 때만 짧게 모입니다.
- 주중 백로그 정리 15분: 다음 작업의 요구사항·의존성·추정 정리.
- 주말 리뷰 20분: 문서 설명보다 실제 실행/산출물을 보여주고 수용 기준 확인.
- 회고 10분: 잘된 점 1개, 막힌 점 1개, 다음 주 변경 1개를 팀 허브에 기록.
- 막힘은 발생 당일 공개. 하루 넘게 풀리지 않으면 팀장이 함께 해결하거나 범위를 축소.

## 추정·상태·완료

SP 1/2/3/5는 상대 난이도 초안이며 시간·개인 평가 점수가 아닙니다. 첫 주 실적과 가용시간으로 다시 추정합니다. 5SP 작업은 착수 전에 1~2일 단위 하위 작업으로 나눕니다. 개인 동시 진행은 1개를 기본으로 합니다.

상태: Backlog → Ready → In progress → Review → Done. 막힘은 상태와 별도로 Blocked로 표시하고 원인·도움 요청·재확인일을 적습니다. 제목의 S번호는 목표 스프린트이며 실제 상태를 의미하지 않습니다.

**Ready:** 담당·완료 기준·선행 작업·리뷰어·검증 방법이 정해짐.
**Done:** 완료 기준 충족 + 검증 증거 + 동료 검토 + 문서 반영 + 해당 PR 병합/산출물 반영. 코드 작성만으로 완료 처리하지 않습니다.

C# 런타임 변경은 `dotnet build Assembly-CSharp.csproj`, 에디터 변경은 Editor 프로젝트도 빌드합니다. 동작 변경은 Unity Console·Play Mode·관련 씬을 확인합니다. 문서만 변경하면 `git diff --check`를 사용합니다.

## 범위 변경과 선택 기능

회피·전투 루프·보스·핵심 연출·ML 데이터 수집/학습/게임 적용·검증은 필수입니다. **가드/패링과 QR 휴대폰 웹 컨트롤러만 선택 백로그**로 유지합니다.

QR 컨트롤러는 시간이 가능하면 진행합니다. S7에서 ML 포함 필수 기능과 차단 오류가 정리된 뒤 남은 가용시간을 보고 팀장이 결정합니다. 11/16 동결 전 구현·검증이 가능한 작은 범위만 착수하고, 어렵다면 후속 개발로 이월합니다. 데이터 수집·모델 검증·11/23 마감을 줄여 확보하지 않습니다.

데이터가 부족하면 수집 보완과 모델/특징량의 단순화를 먼저 검토합니다. 일정이 밀려도 ML을 임의로 선택 기능으로 낮추지 않고 팀장이 범위와 수행량을 조정합니다. 새 보스/스테이지·추가 아트·선택 기능부터 줄입니다.
